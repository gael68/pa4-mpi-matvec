MPI_Allgather(x, nlocal, MPI_DOUBLE, xbuf, nlocal, MPI_DOUBLE, comm);
Say this

The matrix is split by rows: each process owns n/p full rows of A and the matching n/p entries of x. To compute its part of y, a process multiplies each of its rows by all of x, but it only holds a slice. So before the local loop, every process needs every other process's slice. That is exactly MPI_Allgather: each process contributes nlocal doubles and gets back the whole vector in xbuf, in rank order, which is also the order of the rows.

How I checked it. The driver recomputes y sequentially on rank 0 and prints a discrepancy line for any element that differs. My job script counts those lines. As an independent check, the driver's A and x give a closed form for the last element, y[n−1] = 2(n−1)·n(n−1)/2 + (n−1)n(2n−1)/6, and every run matches it exactly.

Why Allgather and not Gather + Bcast, or Bcast alone?

Each process starts with a different piece and every process needs all pieces. Bcast sends one process's data to everyone, which doesn't fit. Gather to rank 0 followed by Bcast works but takes two collectives and funnels everything through rank 0. Allgather does it in one call, and the library can use recursive doubling (log p steps) or a ring.

Why are small-n times faster at p = 1 than p = 8?

At n = 8 there are only 64 multiply-adds. The fixed cost of an MPI collective (microseconds) is far larger than the work, so adding processes only adds overhead. Parallelism pays off only when the work per process outweighs that overhead.

What if n isn't divisible by p?

The driver assumes it is (nlocal = n/numtasks). Otherwise the last rows are never assigned. The fix is MPI_Scatterv/MPI_Allgatherv with per-rank counts and displacements.

Why is the floating-point comparison exact?

All inputs are small integers, and each row is summed in the same order (j = 0…n−1) by the parallel code and by the check. The largest value, about 4.4 × 1013, is below 253, so every partial sum is exact in a double.

Task 2 · Sequential complexity

10 pts
4Theoretical analysis: Θ(n²)
3Times for n = 1000 … 32000 with one task: table

Say this

For each of the n rows we do n multiply-adds, so the work is n² multiply-adds, 2n² flops. We also read all n² matrix entries exactly once and never reuse them. The model is T₁(n) = t_c · n². Doubling n should multiply the time by 4, and it does: the ratios are 4.05, 4.17, 3.93, 3.98, 3.96. Time divided by n² stays at about 1.0 ns from n = 1000 up, so the fitted constant is t_c = 1.006 ns.

Deviations, and what causes them

  • The algorithm is limited by memory bandwidth, not by arithmetic. 1 ns per element means 8 bytes per ns, about 8 GB/s, which is roughly what one EPYC core can stream from DRAM. The core could do several multiply-adds in that time, so t_c is really the cost of fetching one matrix entry.
  • Small n costs more per element (1.36 ns at n = 250). MatrixVectorMultiply has fixed costs: malloc of xbuf, the MPI_Allgather call (about 3 µs even at p = 1) and the timer. At n = 250 that overhead is a visible share of a 0.08 ms run.
  • A small bump where A outgrows the 16 MB L3 (n ≈ 1450). Just below that, A is still partly in cache from the scatter; above it, every access goes to DRAM.
  • Run-to-run variation is under 3% (stdev ≤ 0.006 s at n = 16000).
Why time only one task through mpirun instead of a plain sequential program?

The handout asks for the mvm program with one task. With p = 1 the Allgather is a local copy, so this is the sequential algorithm plus a few microseconds of MPI overhead. It's also the T₁ used for the speedups in Task 5.

Why is the graph a parabola and not a straight line?

The x-axis is n, the matrix dimension, but the work grows with n², the number of matrix entries. Plotted against n² it would be a straight line.

Task 3 · Parallel runtime model

10 pts
4A model with both computation and communication
3Expressed in t_s, t_w, p and n
3Each part derived and explained

Only MatrixVectorMultiply is modelled; the driver's scatter, gather and check are excluded, as the handout says. That is also exactly the span the driver's timer covers.

1. Computation

Each process owns n/p rows of length n and does one multiply-add per entry. All processes work at the same time, so:

T_comp = t_c · n · (n/p) = t_c · n² / p

2. Communication: the allgather

Every process contributes m = n/p words and receives the other (p−1)·n/p. With recursive doubling (hypercube allgather) there are log₂ p steps. In step i each process exchanges the 2i−1·n/p words it has collected so far:

T_comm = Σ_{i=1}^{log p} ( t_s + t_w · 2^{i−1} · n/p ) = t_s · log₂ p + t_w · n · (p−1)/p

The t_s term counts message startups (one per step). The t_w term counts words moved: almost all of x, n(p−1)/p ≈ n, whatever p is. A ring allgather moves the same words but pays (p−1) t_s startups.

3. Total, speedup, efficiency

T_p = t_c · n²/p + t_s · log₂ p + t_w · n · (p−1)/p
S = T₁ / T_p = t_c n² / T_p E = S / p
  • Overhead. T_o = p·T_p − T₁ = t_s · p log p + t_w · n(p−1).
  • Cost-optimal while p·T_p = Θ(n²), which holds for p = O(n).
  • Isoefficiency. Keeping E constant needs t_c n² ∝ t_w n p, so n ∝ p and the work W = n² must grow as Θ(p²).

Say this

Plugging in n = 32000 and p = 8: computation is 1.006 ns × 32000² / 8 = 129 ms. Communication is 0.144 µs × 3 + 0.55 ns × 28000 ≈ 16 µs. Communication is about 0.01% of the total, so the model predicts nearly perfect speedup. The algorithm moves O(n) words but does O(n²/p) work, so for large n the computation dominates.

Your measured allgather is slower than the model. Why?

Inside mvm the slowest rank's allgather takes 0.2–0.8 ms at n = 32000, against about 16 µs predicted. Most of that is waiting, not moving data: the allgather is the first synchronizing call after the scatter, so ranks that arrive early wait for rank 0, which arrives last. Called back-to-back on its own (commbench), the same allgather takes 127 µs at p = 8. That is still more than the two-rank ping-pong predicts, because eight ranks copy through shared memory at once. Either way it's under 0.5% of the runtime, so the conclusion stands.

What's the Big-O of the parallel algorithm?

Θ(n²/p + log p + n). It reduces to Θ(n²/p) when n ≫ p.

Say this

Up to p = 4 the speedup is almost linear, as the model predicts, because communication is negligible. At p = 8 it flattens to 4.3. The model doesn't predict that, and communication isn't the cause: I timed the allgather separately and it's under 0.5% of the time. The cause is memory bandwidth. mpirun placed all 8 ranks on cores 32–39, which on an EPYC 7742 is one 8-core chiplet (CCD). The chiplet's link to memory tops out around 37 GB/s, and 8 ranks streaming A need about 64 GB/s. When I ran the same program with the ranks spread across sockets, p = 8 reached 7.9×.

The refined model

The model treats t_c as a constant, but t_c is really a bandwidth cost: 8 bytes per element. When p ranks share one memory link of bandwidth B, the computation can't run faster than the link can deliver:

T_comp = n² · max( t_c / p , 8 bytes / B ), B ≈ 37.2 GB/s for one CCD

This predicts 4.68× at p = 8, against 4.33× measured.

Proof: same 16 cores, different placement

To rule out everything except placement, I reran the program in the same kind of 16-core RM-shared allocation, changing only how mpirun maps the ranks. The job got cores 32–46 and 51. With the default --map-by core, the 8 ranks fill cores 32–39 (one CCD). With --map-by l3cache they go round-robin over the 4-core L3 clusters (cores 32, 33, 36, 37, 40, 41, 44, 51), so each cluster's memory path carries only two ranks.

Is the 2.02× at p = 2 superlinear?

Barely, and within noise. It can happen when each rank's share fits better in its own cache (L2 is private per core), but at n = 32000 the halves are still 4 GB each, so it's mostly measurement variation.

How would you get closer to linear speedup?

Spread the ranks so they don't share one memory path. I measured this: in the same 16-core allocation, --map-by l3cache takes p = 8 from 4.61× to 7.15×. On a whole node, spreading across sockets gives 7.9×. More nodes would also help, since every node brings its own memory bandwidth. Communication is not the bottleneck at this size.

What's Amdahl / Gustafson here?

There is almost no serial fraction inside MatrixVectorMultiply, so Amdahl isn't what limits us; a shared hardware resource is. Following Gustafson, growing n with p keeps the efficiency high, because per-process work grows as n²/p while communication grows only as n.

The algorithm, in three phases

Each of the p processes owns b = n/p consecutive rows of A (an n × n matrix of doubles) and builds its own rows from the global indices: A[i][j] = i·n + j. Think of its rows as p blocks of b × b. Block k of process r belongs, transposed, to process k.

  1. Local transpose (pack), transpose.c:75–87. Transpose each b × b block into a send buffer, block k at offset k·b². The loop is tiled 64 × 64 so the column-order writes stay in cache.
  2. Exchange, transpose.c:90. MPI_Alltoall sends block k to process k and receives one block from everyone. Every process sends a different block to every other process, which is exactly what all-to-all personalized communication does.
  3. Unpack, transpose.c:93–98. Received block k becomes columns k·b … (k+1)·b−1 of the local rows of Aᵀ, one memcpy per row.

Then transpose.c:112–117 checks every element: B[i][j] == A[j][i]. It prints "correct" or "FAILED", and for n ≤ 8 it prints the result as well.

Model

local pack: t_m · n²/p (every local element moved once, strided writes)
MPI_Alltoall: (p−1) · ( t_s + t_w · n²/p² ) (pairwise exchange: one b×b block to each other rank)
unpack: t_u · n²/p (contiguous copies, t_u < t_m)
T_p = (t_m + t_u) · n²/p + (p−1) · t_s + t_w · n² (p−1)/p²

Unlike mvm, communication and computation are the same order here. Both scale as n²/p, so the transpose has no compute-heavy term to hide communication behind: whatever is moved locally also crosses the network. Expected speedup is at most linear, and lower whenever t_w is large compared with t_m.

Say this

The pack phase behaves like the model's t_m·n²/p term: it falls from 0.91 s to 0.17 s. The alltoall doesn't. The model, with t_w from ping-pong, predicts 7 × (0.14 µs + 0.55 ns × 4 M words) ≈ 15 ms at p = 8, but I measured 139 ms. The ping-pong t_w was measured with one pair of ranks alone. In an alltoall all 8 ranks copy at the same time through shared memory on one chiplet, so they share the same ~37 GB/s link I found in Task 5. The total traffic is 8n²(p−1)/p ≈ 1.8 GB, copied twice (into and out of the shared-memory buffer): about 3.6 GB ÷ 37 GB/s ≈ 97 ms, close to what I measured. So on one node the effective t_w grows with p, and the transpose, which moves as much data as it computes on, tops out at about 2.8×. On a full node with n = 32000, where new ranks land on fresh chiplets, it reached 8.1× at 16 processes.

Why MPI_Alltoall and not Send/Recv or Alltoallv?

The pattern is all-to-all personalized: every process has a distinct block for every other process. MPI_Alltoall states that in one call and lets the library choose the algorithm (pairwise exchange for large messages, Bruck for small ones). Hand-written Send/Recv would serialize or risk deadlock. Alltoallv is only needed when block sizes differ, for example when p doesn't divide n.

Why do you still need a local transpose after the Alltoall?

The Alltoall only moves blocks between processes; each b × b block arrives in its original orientation. Element (i, j) of a block has to become (j, i), and that is the local transpose. I do it before sending, so the receiver only copies rows.

Why does tiling help?

Reading a row of A is sequential, but writing it transposed jumps b doubles each step, touching a new cache line and often a new page. An untiled loop touches b lines per row and evicts them before the next row reuses them. A 64 × 64 tile touches only 64 lines, which stay in L1/L2 until all 8 doubles of each line are written. It cut pack time 19% at p = 1 (1.125 s → 0.914 s).

How much memory does it use?

Four n²/p arrays per rank: A, the send buffer, the receive buffer and B. At n = 16000 and p = 1 that's 8 GB, which fits the 32 GB a 16-core RM-shared job gets. The n = 32000 runs (32 GB at p = 1) used an exclusive RM node.

Could you avoid the pack with MPI datatypes?

Yes. An MPI_Type_vector describing a strided column block lets MPI_Alltoall read straight from A. The strided copy still happens, just inside the library, so the cost moves rather than disappears.
